当前实现摘要

当前仓库已经不是纯设计文档状态，而是一个 设计优先、早期后端接线 的 Python runtime。主入口 main.py 负责读取 YAML、校验并生成 LaunchConfig；ControllerCore 负责把本地可测试的 rollout、queue、trainer、weight registry、GPU lease/offload 串起来；Ray 层已经把 actor graph、资源放置和 vLLM/FSDP2 backend adapter 接起来。

要注意一点：RayDriver.train() 的启动语义由 YAML 控制。run.start_ray_actors: false 时返回规划后的 backend-integrated runtime plan；run.start_ray_actors: true 时才会启动真实 Ray actor graph。actor wrapper 会懒构造 VllmRolloutBackend 和 Fsdp2TrainerBackend，但 CPU-only 最完整的端到端训练形态仍是 scripts/smoke_local_runtime.py 的 deterministic local iteration。

结论：现在的代码已经把交互协议、状态机、资源规划、Ray actor graph 和 backend adapter 连起来了；真实 GPU 训练还需要满足 Ray/vLLM/PyTorch/FSDP2 依赖、模型与 checkpoint artifact，以及多 rank rendezvous。

从 YAML 到 LaunchConfig

用户启动路径是 YAML-first：训练参数、拓扑、role class、并行维度都在 docs/examples/disaggregated.yaml 或 docs/examples/collocated.yaml 中描述，CLI 不提供逐字段覆盖。

main.py 读取配置。 load_launch_config(args.config) 先用 yaml.safe_load 读 YAML，再用 RuntimeConfig.model_validate 做结构化校验。
用户模式归一化。 用户只写 collocated 或 disaggregated；内部 canonical mode 分别是 fully_sync 和 standalone_hybrid。
跨字段约束。 RuntimeConfig._validate_cross_fields() 校验 trainer.num_ranks == shared_gpus、rollout.num_replicas * gpus_per_replica == rollout_only_gpus + shared_gpus、TP 分组可整除、FSDP world size 对齐等。
GPU plan 自动展开。 LaunchConfig.from_runtime_config() 调用 _build_gpu_plan()，把数量型 YAML 展开成 rollout_replicas、rollout_workers、trainer_ranks。
启动开关。 run.start_ray_actors 是是否真正创建 Ray actor graph 的唯一 YAML 开关；示例默认 false，但仍会生成带 vLLM/FSDP2 adapter 参数的 ray_launch_plan。
checkpoint 位置。 trainer.checkpoint_dir 进入每个 TrainerRankActor 的 backend config，rank0/exporter 用它写出 versioned checkpoint 供 rollout/vLLM reload。

这正好对应你前面要求的“不要手动指定 gpu id，只给数量”。例如 disaggregated 示例只写 rollout_only_gpus: 4、shared_gpus: 4、rollout.data_parallel_size: 4、rollout.tensor_parallel_size: 2、trainer.num_ranks: 4。运行 resolved config 后，系统决定具体映射：

rollout-dp-0: gpu0, gpu1     rollout_only
rollout-dp-1: gpu2, gpu3     rollout_only
rollout-dp-2: gpu4, gpu5     shared with trainer
rollout-dp-3: gpu6, gpu7     shared with trainer

trainer-rank-0: gpu4
trainer-rank-1: gpu5
trainer-rank-2: gpu6
trainer-rank-3: gpu7

GPU 拓扑与共享 GPU

当前实现没有继续使用“一个 heavy GpuSlotActor(num_gpus=1) 托管 rollout/train role”的模型。取而代之的是两个更明确的层次：

  • 放置层：Ray custom resources，例如 rollout_gpu_4 和 train_gpu_4。rollout 之间不重复，trainer 之间不重复；但 rollout 和 trainer 可以被系统安排到同一个物理 GPU id。
  • 执行门控层：GpuLeaseManagerCore 记录每张 GPU 当前 active role、holder、lease epoch。只有持有当前 lease 的 role 才能执行 CUDA 相关工作。

为什么这样实现？Ray 的 num_gpus token 是独占调度资源，不适合两个长驻 actor 同时“声称”自己占有同一张卡。当前代码把 Ray token 拆成 role-specific custom resource，让 placement 可表达“rollout 集合内不重复、trainer 集合内不重复、rollout/train 可重叠”，然后用 GpuLeaseManagerCore.assert_active() 和 lease epoch 做运行时互斥。

Ray actor 启动图

build_ray_launch_plan() 生成声明式 RayLaunchPlan，里面有 CPU 控制 actor、rollout replica/controller/worker、trainer rank、reward、queue、registry、metrics。RayClusterController 负责先连接已有 Ray cluster，address=auto 连接失败时创建本机 cluster；随后 RayActorGraphLauncher 把 plan 转成真实 Ray actor graph。

这个 plan 的一个关键 invariant 在 RayActorGraphLauncher._validate_no_ray_gpu_tokens()：所有长驻 actor 的 num_gpus 必须是 0。rollout 侧由 RolloutReplicaControllerActor 按 TP 组持有 resources={"rollout_gpu_i": 1, ...}，trainer 侧由 TrainerRankActor 持有 resources={"train_gpu_i": 1}，运行时再叠加 lease token。disaggregated 示例当前会生成 25 个 actor spec，且没有任何 actor 请求 Ray GPU token。

一轮 RL 训练流程

当前最完整、可执行的走读入口是 ControllerCore.run_smoke_iteration(prompts)。它模拟一轮 PPO/GRPO 类训练中最关键的数据闭环：旧策略生成样本，trainer 消耗样本并导出新权重，rollout 激活新权重后继续采样。

初始化权重。 bootstrap_initial_weight() 用模型路径生成 WeightMeta(version_id=0)，注册到 WeightRegistryActorCore，再调用 _activate_weight_for_rollout()。
暂停 rollout 做权重激活。 RolloutManagerCore.pause_for_weight() 暂停发新请求；registry 进入 ACTIVATING；每个 rollout replica 调 activate_weight() 并 ack；所有 ack 到齐后变成 ACTIVE_GLOBAL。
投喂 prompt 并持续 rollout。 submit_prompts() 进 backlog；pump_rollout_until_blocked() 根据 output queue 水位、in-flight 容量和 max budget 派发请求。
生成样本。 RolloutReplicaControllerRole.generate() 验证 rollout leases、检查 active policy version、生成 SampleRecord，包含 tokens、old_logprobs、reward、weight checksum 和 lease metadata。
样本入队。 SampleQueueActorCore.submit_sample() 按 TTL、policy lag、high watermark、dedupe 决定 accept/drop。
切入 train window。 enter_train_window() 对每个 shared GPU 调用 GpuResidencyManagerCore.enter_train()：rollout draining/offloaded，trainer hydrate，lease role 从 rollout 切到 trainer。
保留 batch 并训练。 TrainerCoordinatorCore.reserve_batch() 从 queue 拿 TrainBatch；所有 TrainerRankRole.optimize() 在 trainer lease 下执行。
发布新权重。 rank0 调 export_weight() 产生 WeightMeta(version_id=1)，registry 注册；queue 对 batch ack。
回切 rollout。 return_to_rollout() 让 trainer offload、rollout hydrate，lease role 回到 rollout，再激活新权重，开始下一轮。

本地 smoke 输出验证了这条链路：一次 prompt 会产生一个 sample、一个 train batch、4 个 trainer rank stats，权重从 v0 变为 v1，shared GPU 在 train window 中处于 TRAINER_ACTIVE，结束后回到 ROLLOUT_ACTIVE。

Rollout 子系统

rollout 的当前设计分三层：全局 rollout manager、每个 DP replica 的 controller、以及 vLLM TP backend。CPU-only smoke path 仍用 RolloutReplicaControllerRole.generate() 生成确定性样本；真实 Ray actor 路径已经在 RolloutReplicaControllerActor 中构造 VllmRolloutBackend，按一个 DP replica 的 TP GPU 组激活权重并调用 vLLM generate。

组件 代码位置 职责
RolloutManagerCore runtime/coordinators.py 维护 prompt backlog、round-robin 选择 replica、in-flight 计数、queue 水位背压、权重激活期间 pause/resume。
RolloutReplicaControllerRole runtime/roles.py CPU-only deterministic fallback，代表一个 DP replica，持有多个 TP worker id，激活权重并生成样本；每次生成前检查所有 GPU leases。
RolloutReplicaControllerActor runtime/ray/actors.py Ray 路径的真实 rollout wrapper：接收 replica_id、gpu_ids、worker_ids 和 backend_config，构造 VllmRolloutBackend；activate_weight() 同步 role 状态并调用 backend；generate() 把 vLLM 输出转为 SampleRecord。
RolloutWorkerRole runtime/roles.py 单 TP worker 的逻辑 holder surface，持有一个 GPU id、TP rank、active policy version 和 lease epoch；当前 Ray placement 不再让 worker actor 持有 rollout_gpu_i 资源，资源由 replica controller 按 TP 组持有。
VllmRolloutBackend runtime/backends/vllm_backend.py 校验 rollout leases、设置 CUDA_VISIBLE_DEVICES、懒加载 vLLM engine，激活权重，调用 engine.generate()，把 vLLM 输出归一化为 GenerationOutput 并可转成 SampleRecord。

真实 Ray placement 的关键变化在 build_ray_launch_plan()：每个 RolloutReplicaControllerActor 的 resources 是该 replica 的完整 TP GPU 组，例如 {"rollout_gpu_4": 1, "rollout_gpu_5": 1}；RolloutWorkerActor 仍存在，但 resources={}，用于保留 TP worker 的逻辑 holder/metadata 边界。

背压逻辑在 dispatch_from_backlog() 中：如果 output queue depth 达到 queue_high_watermark，直接不派发；否则 request budget 取 queue capacity、rollout capacity、backlog length 和外部 max limit 的最小值。

request_budget = min(
    output_queue_high_watermark - output_queue_depth,
    max_in_flight - len(_in_flight),
    len(_input_backlog),
    max_new_requests,
)

这对应你提出的“rollout 并行度较高，当 output queue 水位不太高时，一直给新的数据进去 rollout”。目前是 pull/tick 风格，后续在真实 ControllerActor 中可以把它变成持续 pump loop。

Queue 与权重注册表

SampleQueueActorCore 是 rollout 与 trainer 之间的样本边界。它不直接复制大样本，而是保存 SampleRef，其中 object_ref 未来可以承载 Ray ObjectRef；当前 smoke path 直接放本地 SampleRecord。

队列动作 约束 失败/丢弃语义
submit_sample 去重、TTL、policy lag、queue high watermark DROPPED_TTL、DROPPED_POLICY_LAG、DROPPED_HIGH_WATERMARK
reserve_train_batch 按 max_sequences / max_tokens 选样本，并再次过滤过期和 policy lag 没有可用样本时返回 None
ack_batch trainer 成功后确认 batch 未知 batch 抛 QueueError
release_batch trainer 失败时把未 ack 样本放回 pending 未知 batch 抛 QueueError

WeightRegistryActorCore 管权重版本状态。它的关键点不是单纯保存最新权重，而是让权重激活经过所有 rollout replica ack：REGISTERED -> ACTIVATING -> ACTIVE_GLOBAL。这保证 rollout worker 不会在部分节点还没切权重时就把新 policy 当作全局可用版本。

policy version 是硬边界：SampleRecord、SampleRef、TrainBatch 都携带 policy version 信息；partial rollout 时还可以用 PolicySegment 记录不同 token 段的行为策略版本。

Trainer 与 train window

Trainer 侧有两类对象：TrainerCoordinatorCore 管全局 world size、rank assignment 和 batch reservation；Ray 路径的 TrainerRankActor 通过 build_trainer_backend() 构造 Fsdp2TrainerBackend 或 FakeTrainerBackend。CPU-only smoke path 仍可以直接用 TrainerRankRole 做 deterministic optimize。

Fsdp2TrainerBackend 现在不再固定抛“未实现”：它会懒导入 torch/transformers/FSDP2，设置当前 rank 的 CUDA_VISIBLE_DEVICES，加载 HF causal LM 与 tokenizer，初始化 AdamW，对 TrainBatch.sample_refs[*].object_ref 中的 SampleRecord 拼接 prompt/response 后做 LM loss step，并由 rank0 把版本化 checkpoint 写到 trainer.checkpoint_dir/version-N。

共享 GPU 的 train window 是最核心的状态机。GpuResidencyManagerCore.enter_train() 和 exit_train() 会把 lease 与 offload/hydrate hook 串在一起：

ROLLOUT_ACTIVE
  -> ROLLOUT_DRAINING
  -> ROLLOUT_OFFLOADED
  -> TRAINER_HYDRATING
  -> TRAINER_ACTIVE

TRAINER_ACTIVE
  -> TRAINER_OFFLOADED
  -> ROLLOUT_WAKING
  -> ROLLOUT_ACTIVE

这套状态机的价值是：rollout actor 和 trainer actor 可以是不同 failure domain，但同一张 shared GPU 任意时刻只有一个 active role。每次切换都会产生新的 lease_epoch，旧 lease 不能继续通过 assert_active()。

失败类型 触发位置 当前行为
SHARED_GPU_OFFLOAD_FAILED offload hook 失败或残留显存超预算 返回结构化失败，状态进入 DEGRADED，Controller 记录 metrics 并抛错。
SHARED_GPU_HYDRATE_FAILED hydrate hook 失败或残留显存超预算 返回结构化失败，状态进入 DEGRADED。
SHARED_GPU_TOGGLE_TIMEOUT offload/hydrate duration 超过配置预算 返回 timeout 事件，避免 silent hang。

vLLM / FSDP2 后端边界

后端代码当前是“Ray actor 已接入、可导入、可测试、懒加载真实依赖”的 adapter 实现，避免在普通配置解析或单测中强制安装 vLLM/PyTorch GPU 环境。真正调用真实后端发生在 Ray actor 方法里：rollout 进入 RolloutReplicaControllerActor.activate_weight/generate，trainer 进入 TrainerRankActor.initialize_rank/hydrate/optimize/export_weight/offload。

vLLM rollout backend

RolloutReplicaControllerActor 构造 VllmRolloutBackend；backend 校验 GPU/holder lease、拒绝重复 GPU lease、按 gpu_ids 设置 CUDA_VISIBLE_DEVICES，再懒构造 vLLM engine；generate() 检查 active weight version，并把 vLLM request output 归一化为 GenerationOutput。

Fake trainer backend

FakeTrainerBackend 可完整 initialize/hydrate/optimize/export/offload，用于 CPU-only 单测和 smoke。

FSDP2 trainer backend

TrainerRankActor 构造 Fsdp2TrainerBackend；backend 会加载 HF model/tokenizer、初始化 optimizer、执行 LM loss optimize、offload 到 CPU，并由 rank0 save_pretrained() 后返回新的 WeightMeta。真实多 rank FSDP2 依赖 checkpoint 目录和 rendezvous/store endpoint。

actor 启动开关

RayDriver.train() 默认返回 execution_status=planned_backend_integrated；只有 run.start_ray_actors=true 时才调用 start_actor_graph()，并可在测试里注入 fake actor builders。

因此，当前代码里的“训练”有两种语义要区分：

  • 协议和状态机训练：run_smoke_iteration() 已经完整执行，证明组件能组合。
  • 真实模型训练：run.start_ray_actors: true 会先执行 Ray connect-or-create，再启动 actor graph；vLLM engine 与 FSDP2 optimizer/export 路径已挂到 actor adapter，但要真正跑通仍需要本机依赖、模型 artifact、trainer.checkpoint_dir、多 rank rendezvous 和 GPU 集成测试。
RayDriver.train()
  -> build_ray_launch_plan()
  -> RayClusterController.ensure_initialized()
  -> RayActorGraphLauncher.start()
  -> RolloutReplicaControllerActor(..., backend_config={gpu_ids, holder_ids, tensor_parallel_size})
  -> TrainerRankActor(..., backend_config={backend=fsdp2, model_path, checkpoint_dir, rank/world_size})
