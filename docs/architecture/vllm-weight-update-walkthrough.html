训练后如何把新参数更新到 vLLM serving engine

这份走读按当前仓库代码解释一次 train step 结束后的权重发布、传输规划、rollout 暂停、vLLM backend 激活和全局 ack。重点结论是： nano-rl 已经把控制面和 hook 铺好，但 stock vLLM 的真实 in-place 权重热更新还需要一个实现了 activate_weight、load_weight 或 load_weights 的 engine/adapter。

入口

RayTrainingLoop._run_train_step() 训练、导出、注册，再调用 _activate_weight_for_rollout()。

控制面

WeightTransferPlanner 决定每个 rollout replica 从 artifact、shared GPU reshard 或 Ray object ref 取权重。

执行面

RolloutReplicaControllerActor.activate_weight() 把 WeightMeta 和 transfer source 交给 VllmRolloutBackend。

当前边界

_notify_engine_weight() 是热更 hook。默认 vllm.LLM 若没有这些方法，当前函数会跳过真实加载。

一句话答案

每次训练完以后，trainer rank 0 产出一个新的 WeightMeta(version_id=N)， driver 把它注册到 WeightRegistry，暂停 rollout 派发，为每个 rollout replica 计算 WeightShardSource，然后逐个调用 rollout actor 的 activate_weight(meta, leases, source)。 rollout actor 再调用 VllmRolloutBackend.activate_weight()，后者在合法 rollout lease 下构建或唤醒 vLLM engine， 并尝试调用 engine 的权重加载 hook。所有 replica ack 后，这个版本才变成 active_global。

代码锚点： nano_rl/runtime/ray/training.py lines 239-279, 339-371； nano_rl/runtime/ray/actors.py lines 203-220； nano_rl/runtime/backends/vllm_backend.py lines 182-219, 591-603。

权重传输计划

WeightTransferPlanner 不直接搬 tensor，它只产出控制面计划：每个 rollout replica 应该从哪里拿到版本 N 的 shard。 这让 trainer export、registry 状态机、vLLM 激活彼此解耦。

source kind 什么时候出现 语义 代码位置

artifact_pull rollout-only GPU 没有 trainer shard 从 WeightMeta.artifact_uri 或 manifest hydrate。默认 locality_aware_checkpoint 会用这个兜住 rollout-only GPU。 weight_transfer.py lines 127-144

rollout 激活

_activate_weight_for_rollout() 是新权重进入 serving 路径的主控函数。它先暂停 rollout manager， 避免旧派发和新激活并行，然后 registry 进入 activating，最后按 replica 顺序调用 actor。

  1. 1

    跳过重复版本。 如果 _rollout_active_weight_version 已经是当前版本，直接返回，避免重复激活。

    代码：ray/training.py lines 339-342。

  2. 2

    生成 transfer plan。 planner 使用 WeightMeta、rollout replica 列表和 trainer rank 列表生成 per-replica source。

    代码：ray/training.py lines 343-352。

  3. 3

    暂停、begin、逐个 activate。 每个 replica 拿当前 rollout lease 和自己的 source，调用 activate_weight()。

    代码：ray/training.py lines 354-363。

  4. 4

    ack 到全局活跃。 每个 replica 成功后调用 registry ack。所有 required replica 都 ack 后，registry 把版本状态切到 active_global。

    代码：weight_registry.py lines 42-67。

def _notify_engine_weight(engine, meta, *, transfer_source=None):
    for method_name in ("activate_weight", "load_weight", "load_weights"):
        method = getattr(engine, method_name, None)
        if method is not None:
            method(meta, transfer_source=transfer_source)
            return

serving 时如何保证版本

rollout manager 派发 request 时带上 target_policy_version。vLLM backend 在生成前检查 _active_weight.version_id 必须等于目标版本；生成后的 sample 也带 policy_version 和 weight_checksum，后续 queue 和 trainer 可以按版本做过滤或统计。

实现边界和风险

最重要的边界

当前默认 engine factory 返回的是 vllm.LLM(**kwargs)。代码只会在 engine 暴露 activate_weight、load_weight 或 load_weights 时真正通知加载新权重。 如果 stock vLLM engine 没有这些方法，_notify_engine_weight() 会静默返回，只有 nano-rl 的 _active_weight 元数据被切换。

怎么补齐真实热更

需要一个 vLLM adapter/engine 扩展实现这些 hook，并根据 WeightShardSource.kind 做三件事之一：从 shared GPU trainer state reshard、从 artifact/manifest hydrate、或从 Ray object ref materialize。

reload 路径

如果采用 teardown_and_reload，wake() 可在 engine 为 None 时用当前 _active_weight 重建 engine。当前配置默认更偏向 vllm_sleep，适合未来 in-place update hook。

失败处理

activation 任一 replica 失败时 registry 会 mark_failed，rollout manager 在 finally 中 resume。 训练 batch 在 activation 前已经 ack，这符合当前代码，但生产语义是否要 rollback 还需要设计确认。
